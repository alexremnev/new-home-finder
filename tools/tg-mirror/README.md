# tg-mirror

Копирует сообщения, приходящие вам в Telegram, в ваш собственный чат.

Полностью отдельный инструмент: ничего не импортирует из `worker/`, не трогает базу
скрапера, своя `requirements.txt`, свой `.env`, свой virtualenv. Ломается,
обновляется и удаляется независимо от скрапера. В `pyproject.toml` папка `tools/`
исключена из `ruff` и `mypy` — иначе проверки скрапера начали бы требовать
зависимость, которой у него нет.

## Почему это не бот

Bot API не может прочитать трафик другого бота: бот не имеет доступа к апдейтам
второго бота, Telegram не доставляет боту сообщения других ботов даже в общей
группе, а **исходящие** сообщения бота не видны вообще никому — включая его
самого. Значит решения в виде бота здесь не
существует.

Остаётся очевидное: эти сообщения уже лежат в вашем аккаунте. Скрипт входит **как
вы** по MTProto, читает ваш же диалог с ботом и пересылает новое туда, куда вы
скажете. Токен читаемого бота для этого не нужен.

## Что нужно знать до запуска

**Строка сессии — это живой вход в аккаунт.** Кто её держит, тот залогинен как вы:
без пароля и без кода. Это ближе к cookie на весь аккаунт, чем к паролю. Держите
её в `.env` или в секрет-хранилище, никогда в репозитории. Если утекла — Telegram
→ Настройки → Устройства → завершить сеанс.

**Автоматизация пользовательского аккаунта — не то, для чего аккаунты
предназначены, и Telegram за этим следит.** Читать свои же входящие в человеческом
темпе — мягкий край этого спектра, но риск несёт аккаунт, а не бот. Долгий вход с
одной машины выглядит обычно, повторные входы с меняющихся IP дата-центров — нет.
Это и есть аргумент против GitHub Actions в пользу ноутбука или маленькой VPS.

## Установка

**Windows** (основная машина, где это будет крутиться):

```bat
cd /d D:\projects\new-home-finder\tools\tg-mirror
py -3 -m venv .venv
.venv\Scripts\pip install -r requirements.txt
copy .env.example .env
```

**macOS / Linux:**

```bash
cd tools/tg-mirror
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Свой virtualenv, а не `uv` проекта: Telethon не должен попасть в зависимости
скрапера, а зеркало не должно упираться в его пины версий.

Дальше заполнить `.env`:

1. **`TG_API_ID` и `TG_API_HASH`** — https://my.telegram.org → *API development
   tools* → создать приложение. Это ключ приложения, привязанный к вашему номеру,
   а не токен бота.
2. **`TG_DEST_CHAT`** — куда складывать копии. Свой chat id узнать у
   [@userinfobot](https://t.me/userinfobot). Приватная группа тоже подходит.
3. **`TG_DEST_BOT_TOKEN`** — токен **вашего** бота, @BotFather → `/mybots` → *API
   Token*. Нужен для режима по умолчанию. Откройте своего бота и нажмите Start,
   иначе он не сможет вам написать — Telegram запрещает боту писать первым.
4. **`TG_SESSION`** — получить так:

```bash
python mirror.py login
```

Спросит номер телефона, код из Telegram и пароль двухфакторки, если она включена.
Напечатает строку сессии — вставить её в `.env`.

## Запуск

```bash
python mirror.py once --dry-run --backfill 3   # посмотреть, ничего не отправляя
python mirror.py once --backfill 3             # проверить, что доставка работает
python mirror.py once                          # обычный прогон: только новое
python mirror.py watch                         # висеть на связи и пересылать сразу
python mirror.py watch --via forward           # сохранять фото и форматирование
```

## Фото и ссылки

Сообщения такого бота обычно устроены так: фото сверху, текст, и ссылки в конце. Передаётся
всё это, но в `--via bot` — восстановлением, а не пересылкой, и стоит понимать
почему.

**Фото.** Скачивается и заливается заново через вашего бота. Просто сослаться на
файл по ссылке нельзя: `file_id` принадлежит тому боту, который его видел,
и для другого бота он недействителен. Значит байты действительно едут через вашу
машину. Отключается флагом `--no-media` — тогда в тексте останется пометка
`[photo]`, что вложение было.

Подпись к фото вмещает 1024 символа, а сообщение — 4096. Если текст длиннее, фото
уходит без подписи, а текст следом отдельным сообщением: обрезать хвост на 1024
было бы потерей, а дублировать — выглядело бы как баг. Фото больше 10 МБ уходит
документом (байты целы, Telegram всё равно показывает превью), больше 50 МБ —
только текстом, потому что залить его боту нельзя. Если скачивание сорвалось,
сообщение всё равно доедет текстом.

**Ссылки.** Тут неочевидное: `message.text` показывает не все URL. Их три вида, и
только один виден в тексте:

| Где ссылка | Видна в `message.text`? |
|---|---|
| голый `https://…` в теле | да |
| слово-гиперссылка («Смотреть») | **нет** — URL лежит в entity |
| кнопка под сообщением | **нет** — в тексте её вообще не существует |

Боты-объявления пользуются как раз вторым и третьим — то есть ровно те две ссылки
в конце, которые вам нужны, в тексте не лежат. Скрипт достаёт их из entities и из
inline-клавиатуры и дописывает голыми URL в конец. Голыми, а не гиперссылками,
потому что без parse mode ничего нельзя испортить экранированием. Ссылка, которая
и так видна в тексте, второй раз не печатается.

**Альбом.** Если бот присылает несколько фото одним альбомом, Telegram отдаёт их
как отдельные сообщения, и подпись есть только у первого. Значит первая копия
придёт с текстом, остальные — как `[photo, no text]`. Порядок сохраняется.

**`--via forward`** ничего не восстанавливает: пересылает нативно, от вашего имени.
Фото, форматирование, кнопки и плашка «переслано от» сохраняются как есть, файл
Telegram двигает на своей стороне — то есть ничего не качается. Токен бота не
нужен, но ваш аккаунт должен быть участником чата-получателя.

## Как выглядит копия и как её менять

Заголовка с источником, датой и id сообщения нет: при одном источнике это три
факта, которые никто не читает над каждым алертом, а id полезен в логе, а не в
сообщении.

Формулировки источника, которые не хочется зеркалить дословно, задаются в `.env`
переменной `TG_REWRITES`, а не в коде — формулировки настраиваются, а не
зашиваются:

```
TG_REWRITES=<регулярка>=>NEW ALERT
```

Несколько пар разделяются `;;`. Регистр не важен. Знаки в конце фразы включайте в
саму регулярку (`[!.:]*`), а пробелы — **нет**: `\s` съел бы перевод строки и
склеил замену с первой строкой текста.

Так приходит сообщение:

```
NEW ALERT

£1,950/mo · 2 bedrooms
📍 SE16 · Zone 2

https://hidden/listing
https://portal/view
https://portal/contact
```

Кроме этой подстановки с текстом не делается ничего — всё остальное приходит ровно
как было отправлено.

## Что пишется в лог

Каждый прогон оставляет одну итоговую строку фиксированной формы:

```
==== START 10.08.2026 15:07:01,23
mirror: @the_feed_bot 2 new
mirror: @the_feed_bot sent 2, cursor now 10629
mirror: SUMMARY started 2026-08-10 15:07:01 finished 2026-08-10 15:07:09 sent 2 failed 0
==== END   10.08.2026 15:07:09,44 exit 0
```

Два времени, а не одно: планировщик знает только когда задача запустилась, а не
сколько шла. Разрыв между `started` и `finished` — первое, что интересно, если
прогон подвис на загрузке фото.

`sent` — сколько реально доехало, не сколько нашлось. При частичном сбое (три
новых, два доставлены) будет `sent 2 failed 1`, и курсор встанет на втором.

Читать неделю логов:

```bat
findstr SUMMARY logs\mirror-2026-08-10.log     REM по одной строке на прогон
findstr /V /C:"failed 0" logs\*.log            REM только прогоны с проблемами
```

Логи в `logs\mirror-<дата>.log`, по файлу на день, в git не попадают.

## Курсор

`state.json` рядом со скриптом хранит id последнего пересланного сообщения по
каждому чату. Первый прогон без курсора **не пересылает ничего** и только
записывает точку старта: иначе включение зеркала вылило бы в получателя всю
историю. `--backfill N` берёт последние N, когда это нужно осознанно.

Свои собственные сообщения в диалоге не пересылаются — они и так ваши, а зеркалить
их обратно значило бы удваивать каждый разговор.

Курсор двигается только по фактически доставленным сообщениям. Сбой доставки
останавливает прогон на этом месте, чтобы следующий подобрал остаток, а не
проглотил его молча.

### «Обработано» — это локально, а не в Telegram

Скрипт **не помечает сообщения прочитанными**: ни одного вызова `readHistory` в
коде нет, а чтение истории через `iter_messages` само по себе прочитанность не
меняет. Из этого следуют три вещи, и все три — то, что нужно:

- В телефоне непрочитанные остаются непрочитанными. Зеркало невидимо для вашего
  обычного пользования: счётчик на чате не обнуляется за вас.
- Обратное тоже верно: то, что вы прочитали переписку на телефоне, никак не влияет
  на зеркало. Если бы «обработано» означало «прочитано», прочтение с телефона
  съедало бы сообщение до того, как задача его увидит — поэтому курсор и держится
  отдельно, в своём файле.
- Повторов не будет: `state.json` хранит id последнего доставленного, и следующий
  прогон берёт строго `min_id` больше него.

Обратная сторона — курсор живёт только в этом файле, на этой машине. Удалить
`state.json` значит начать с нуля (прогон запомнит текущую точку и пропустит
накопившееся). Запустить зеркало со второй машины значит получить копии дважды: у
каждой свой курсор.

## Автозапуск на Windows раз в час

Два файла в [win/](win/), в том же стиле, что и [scripts/win/](../../scripts/win/)
для воркера:

- [win/run-mirror.cmd](win/run-mirror.cmd) — один прогон `once` с записью в лог.
  Пути вычисляются от собственного расположения файла (`%~dp0..`), поэтому
  переименование или перенос папки задачу не ломает.
- [win/install-task.cmd](win/install-task.cmd) — регистрирует часовую задачу.

### Шаг 1. Проверить, что вручную работает

Из папки `tools\tg-mirror`, **до** регистрации задачи:

```bat
.venv\Scripts\python mirror.py once --dry-run --backfill 3
```

Должен напечатать 3 последних сообщения от бота и строку «dry run, nothing sent».
Если вместо этого ошибка — она будет одной понятной строкой, чинить надо её, а не
Task Scheduler. Дальше — реальная доставка:

```bat
.venv\Scripts\python mirror.py once --backfill 1
```

Одно сообщение должно прийти в `TG_DEST_CHAT`. Это доказывает всю цепочку целиком.

### Шаг 2. Проверить обёртку

```bat
win\run-mirror.cmd
echo %ERRORLEVEL%
type logs\mirror-*.log
```

Ожидается `0` и в логе строки `==== ... once` и `==== exit 0`. Обёртка проверяется
отдельно от планировщика, потому что 90% проблем здесь: не тот путь, нет venv, не
та рабочая папка.

### Шаг 3. Зарегистрировать задачу

Двойным щелчком или из консоли:

```bat
win\install-task.cmd
```

Он передаёт работу [win/install-task.ps1](win/install-task.ps1) и попросит **пароль
Windows**. Дальше — почему.

### Запуск без входа в систему и из сна

Три настройки, все выставляются установщиком:

| Настройка | Что даёт |
|---|---|
| `LogonType Password` | «Run whether user is logged on or not» — задача идёт, когда вы не залогинены |
| `WakeToRun` | будит машину из сна или гибернации к нужной минуте |
| `StartWhenAvailable` | догоняет пропущенные слоты, если машина была выключена |

Плюс `AllowStartIfOnBatteries` и `DontStopIfGoingOnBatteries` (иначе на ноутбуке от
батареи задача не пойдёт вовсе) и `Hidden`, чтобы не мигало консольное окно.

Отсюда `schtasks` и заменён на PowerShell: ни «будить машину», ни «догонять
пропущенное», ни «работать от батареи» через `schtasks /Create` не выражаются, его
единственный путь к ним — XML-файл в UTF-16, который из `.cmd` писать мучительно.
Командлеты `ScheduledTasks` ставят всё это напрямую.

**Что нужно знать про пароль.** Чтобы запускать задачу, когда вы не в системе,
Windows должен уметь логинить аккаунт сам, поэтому пароль обязателен. Хранит его
Windows в Credential Manager, а не скрипт: на диск и в лог он не попадает, а из
памяти стирается сразу после передачи. Два подводных камня:

- Если вход в аккаунт по **PIN или Windows Hello**, нужен пароль **учётной записи
  Microsoft**, а не PIN.
- **Пустой пароль не подходит** — Windows отказывается запускать неинтерактивные
  задачи для аккаунта без пароля. Это ограничение Windows, обойти нельзя.

Установщик сам поднимет права администратора: сохранение пароля для задачи —
административное действие.

**Про будильник честно.** `WakeToRun` работает из сна и гибернации. Из полностью
выключенной машины не разбудит ничто — там сработает `StartWhenAvailable` при
первой загрузке. И `WakeToRun` может быть перебит планом питания: если *Allow wake
timers* выключен, задача просто не разбудит машину, молча. Установщик это
проверяет через `powercfg` и говорит, если таймеры запрещены — менять ваш план
питания без спроса он не будет. Включается так: Панель управления → Электропитание
→ Настройка схемы → Дополнительные параметры → Сон → Разрешить таймеры
пробуждения.

### Полезные команды

```powershell
Get-ScheduledTaskInfo -TaskName "TG mirror"     # последний результат и следующий запуск
schtasks /Run /TN "TG mirror"                   # прогнать сейчас
Disable-ScheduledTask -TaskName "TG mirror"     # выключить, не удаляя
Unregister-ScheduledTask -TaskName "TG mirror" -Confirm:$false
```

Колонка *Last Run Result* / `LastTaskResult`: `0` — чистый прогон, `1` — в логе
написано, что не вышло.

### Про интервал

Раз в час — это задержка **до часа** между тем, как источник вам написал, и
копией у себя. Ограничения на срок здесь нет: скрипт читает настоящую историю
диалога, а не очередь Bot API, поэтому пропуск в сутки или в неделю не теряет
ничего — при следующем запуске догонит всё с момента курсора.

Если захочется получать мгновенно, вместо задачи запускайте `mirror.py watch` —
процесс висит на связи и пересылает сразу. Часовая задача устойчивее к
перезагрузкам и сну, поэтому для Windows я выбрал её.

## Про GitHub Actions

Workflow специально не добавлен. Две причины: `state.json` между запусками не
сохраняется, так что курсор пришлось бы куда-то выносить, и вход в пользовательский
аккаунт с постоянно меняющихся IP раннеров — ровно тот шаблон, на который Telegram
отвечает обнулением сессии. Домашняя машина для этого подходит лучше.
